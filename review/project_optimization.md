## 初次评审记录（历史）

项目采用 Vue 3、TypeScript、Vite，以及 Cloudflare Pages / D1。已有模块化卡片、账户隔离、收藏与打卡的待同步队列、天气缓存和示例数据标识、模态框焦点管理等基础。主要优化价值集中在数据一致性、部署后功能可用性、日期逻辑和回归验证。

优先级说明：P1 优先处理，会影响数据或核心功能；P2 随后处理，改善可靠性、性能和交互；P3 维护整理。每项均可以作为后续独立实施任务。

## 1. P1：补齐重要日子的保存、离线重试和并发保护

- 证据：`src/App.vue:133` 的 `handleUpdateCustomEvents` 只保存本地偏好，未调用同步；相反，`src/App.vue:77` 在更新模块等偏好时上传整个日程列表。`src/services/sync.ts:182` 上传失败只打印警告，没有加入待同步队列。`worker/index.ts:670` 的 PUT 接口先删除用户所有日程再重建。
- 影响：日常新增、编辑、删除日程不会立即上传；关闭页面或读取旧云端数据后可能丢失本地修改。不同设备上传完整列表可能覆盖彼此修改，切换无关设置也可能触发覆盖。
- 核验：内存模拟断网上传后，待同步操作数为 0，状态仍是 `synced`，用户错误提示为空。
- 建议：事件编辑统一进入按账户持久化的操作队列；优先使用现有单项 POST / DELETE 接口，并为同一事件加入版本或冲突规则；只由事件变化触发上传。
- 验收：新增、编辑、删除均能跨设备同步；离线操作重连后补传；两端修改不同事件不相互覆盖；失败时显示准确状态。

## 2. P1：正确处理云端空日程列表

- 证据：`src/services/sync.ts:168` 仅在 `customEvents.length > 0` 时更新本地。
- 影响：一台设备删除最后一个日程后，其他设备仍保留旧记录；后来上传旧列表可能让已删除事件重新出现。
- 核验：先读取一个云端事件，再将模拟云端列表改为空并刷新，本地仍保留 1 个事件。
- 建议：区分“字段缺失”与“已确认的空列表”；在待同步修改和冲突处理完成后，接受合法空数组。
- 验收：清空事件后，其他设备刷新得到空列表，不恢复默认样例或已删除记录。

## 3. P1：让浏览器安全策略覆盖实际使用的资源

- 证据：`public/_headers:7` 的 CSP 只允许连接同源和 `api.open-meteo.com`，图片仅同源及 data，未声明 `media-src`。实际代码使用 `geocoding-api.open-meteo.com`（`src/services/weather.ts:88`）、第三方头像（`src/components/AccountModal.vue:62`）和外部电台（`src/services/audio.ts:64`、`:74`、`:84`）。
- 核验：线上首页 HEAD 返回 200，响应中的 CSP 与上述配置一致。
- 影响：按浏览器 CSP 规则，海外城市检索、外部头像和网络音频会被阻止。未定义 `media-src` 时回退到 `default-src 'self'`；Web Audio 本地合成音效不属于这一外部电台问题。
- 建议：维护实际资源域名清单，按资源类型添加精确允许项；头像加载失败提供回退；网络音频区分策略阻止、网络失败和播放授权失败。
- 验收：在带生产响应头的环境验证海外检索、真实头像与每个流媒体曲目，而不只使用 Vite 开发页。
- 规则依据：[MDN CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)、[MDN media-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/media-src)。

## 4. P1：统一月历与倒计时的农历日期计算

- 证据：`src/components/MonthCalendarCard.vue:87` 直接截取事件日期的月日，按公历格子匹配，没有检查 `isLunar`。`src/services/calendar.ts:180` 的倒计时则会将农历转换为公历。
- 影响：农历生日在月历中的标记与重要日子倒计时可能落在不同日期；同一天多个事件还会被 `Map<string, string>` 覆盖，只留下一个标题。
- 建议：复用统一的事件日期解析和转换逻辑，为月历所展示的年份计算实际公历日期；一天保留事件数组。明确农历特殊日期及闰月规则。
- 验收：相同农历生日在月历、列表和提醒中指向同一公历日期；同日多个事件可以完整查看。

## 5. P1：验证导入文件和事件接口的完整结构

- 证据：`src/components/SettingsModal.vue:77` 解析 JSON 后直接作为偏好发出；`src/App.vue:78` 随即访问 `newPrefs.selectedCity.name`。`worker/index.ts:672` 将非数组的 `events` 默认为空数组并继续删除全部日程；日期和事件类型也缺少完整校验。
- 影响：合法 JSON 并不一定是合法备份；缺少字段可使页面报错。错误的事件上传载荷可被当成“清空日程”。`src/services/calendar.ts:213` 使用 Date 构造时会顺延不存在的日期。
- 核验：输入 `2026-02-30`，事件计算返回 `2026年3月2日`。
- 建议：增加带版本的备份结构校验与默认字段合并；服务端拒绝错误的列表类型、无效日期和未知事件类型，在全部验证通过后再执行写入。区分公历与农历的有效日期规则。
- 验收：错误备份提示具体原因，不修改已有数据；错误 API 载荷返回 400；不存在的日期不会静默转换成其他日期。

## 6. P1：验证 OAuth 消息来源并完善弹窗生命周期

- 证据：`src/services/sync.ts:328` 的消息监听仅匹配 `event.data.type`，未校验 `event.origin` 或 `event.source`；`worker/index.ts:175` 使用 `postMessage(..., '*')`。`src/services/sync.ts:250` 打开弹窗后没有处理用户主动关闭或授权长时间未返回。
- 核验：内存模拟来自 `https://untrusted.example` 的 OAuth 错误消息，会被接受并修改账户错误提示。成功消息也可触发会话读取和访客合并流程；本次没有验证或证明账户接管。
- 建议：保存预期弹窗引用，严格检查来源及窗口身份，校验消息结构；使用明确目标 origin；关闭、取消和超时均恢复 busy 状态。
- 另需真实授权验证：`worker/index.ts:83` 的会话 Cookie 使用 `SameSite=Strict`，而新 OAuth 绑定在跨站回调中依赖 `userFor(request, env)`（`:277`）。按 Cookie 规则推断，原登录会话可能无法随回调发送，从而新建账户而非绑定现有账户。应在发起绑定时保存与 state 关联的服务端绑定意图，并在回调消费。
- 本地配置问题：`worker/index.ts:102` 总是生成 `http://localhost:8787/.../callback`，README 列出的 URI 未包含该地址；从 127.0.0.1 发起还存在 Cookie 主机变化。应统一回调配置和开发文档。
- 验收：不可信消息无效；关闭弹窗后可再次登录；真实 Google / GitHub 登录、已有账户关联与本地回调都通过端到端验证。
- 规则依据：[MDN postMessage](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)、[MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)。

## 7. P2：使账户切换后的偏好与当前界面一致

- 证据：`src/App.vue:35` 账户变化只重新读取 `prefs`，没有重新应用主题或请求新城市天气；这两项副作用分别只在其他处理函数和挂载时执行。
- 影响：切换到账户中不同的城市后，天气标题可能显示新城市，数据却仍来自原城市；保存的主题也不一定立即生效。
- 建议：统一管理偏好变化的副作用；监视城市坐标和主题，在切换账户时执行，避免重复请求并保留请求竞态保护。
- 验收：账户 A / B 与访客切换时，主题、城市名称和天气数据始终一致。

## 8. P2：统一跨日更新和通知去重

- 证据：`src/components/MonthCalendarCard.vue:11` 的 `now` 在组件创建时固定，今日标记不会随午夜更新；App 与 Header 各有 30 秒计时器。`src/App.vue:223` 的提醒只选第一个符合条件的事件，挂载时再次检查且没有每日去重记录。
- 影响：长时间打开后，日期标题、月历今日标记可能不同步；同一天多个重要事件只有一个被提醒；刷新页面可能重复通知。
- 建议：使用共享的当前日期状态；页面重新可见时重新校准日期；按事件 ID、提醒档位和本地日期记录发送状态，并处理多个符合条件的事件。
- 验收：页面跨午夜保持一致；重复刷新不重复提醒；同一天多个事件都能被覆盖。

## 9. P2：修正本地存储的空值、去重和失败反馈

- 证据：`src/services/storage.ts:183` 的随笔读取把已保存的空数组当成首次使用；`:52` 卡片排序过滤无效 ID，但不去重。部分存储写入异常仅写入控制台，`src/services/sync.ts:17` 则直接忽略异常。
- 核验：保存 `[]` 后读取随笔仍返回 1 条欢迎内容；排序输入两个 `calendar` 会保留两个。
- 影响：删空随笔后刷新，欢迎内容重新出现；异常或导入的重复顺序可能渲染重复卡片；存储失败时用户可能以为数据已经持久化。
- 建议：区分键不存在与已保存空数组；规范化排序时去重；存储函数返回明确结果，保存失败展示可操作提示。
- 验收：空随笔保持为空；重复顺序被规范化；存储不可写时反馈准确。

## 10. P2：减小首页包体，按需加载内容

- 证据：`src/App.vue:4` 起静态导入全部卡片，`:26` 起静态导入多个完整内容库；`src/services/storage.ts` 也集中导入这些内容。关闭模块不会排除其代码和数据。
- 构建结果：首页 JS 859.78 kB，gzip 306.13 kB；CSS 115.49 kB，gzip 21.41 kB。Vite 发出大于 500 kB 的 chunk 警告。
- 建议：先分析包体组成；对账户、设置、大型内容浏览和非首屏卡片使用动态加载；调整集中导入内容库的服务边界，否则仅改卡片为异步仍可能把数据留在主包中。结合实际使用决定哪些模块应该保留即时显示。
- 验收：相同构建口径比较优化前后的首屏资源大小和加载时间，确认不破坏离线显示、内容切换与排序。

## 11. P2：补齐触屏和键盘排序入口

- 证据：`src/App.vue:312` 使用原生 draggable 和 dragstart / dragover / drop 实现卡片排序，没有触屏或键盘替代操作。
- 影响：当前实现的触屏可用性需要实机验证；键盘用户缺少移动卡片的入口。
- 建议：先提供“上移 / 下移”这样的低成本按钮及顺序变更提示；根据触屏验证结果，再决定是否采用 Pointer Events 或排序库。
- 验收：手机触屏和纯键盘均能完成排序，刷新后保留结果。

## 12. P2：将上述问题纳入可重复的回归验证
